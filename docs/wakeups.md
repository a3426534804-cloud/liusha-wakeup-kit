# 自主唤醒与自动脚本

## 原生唤醒的运行方式

提取版 `cc_native.Runtime` 启动一个已有会话的持久 CLI 进程，使用 stream-json 输入输出。

1. 用户消息经 stdin 写入，带唯一 UUID，加入 pending 表。
2. replay acknowledgment 按 UUID 对应到普通聊天 / setup。
3. 没有待确认用户消息时出现的新请求事件，视为运行时自主唤醒。
4. `ScheduleWakeup` 工具结果中的 `scheduledFor` 写成下一次计划时间。
5. `result` 结束一轮，分别记账为 `chat`、`cc_wakeup`、`cc_wakeup_setup`。
6. 唤醒输出为 `[[SILENT]]`、执行失败，或用户已回来等待时，不额外推送一条打断消息；仍保留醒迹和 usage。

这里没有宣称 Python 每隔固定分钟“让模型自己醒来”。Python 管的是进程、事件归属、偏好文件与观察；原生调度是否存在，要检查当前 CLI `init` 事件的工具列表。

## 用户设置的权威性

后台 setup / wake 必须继承最近一次**真实聊天**携带的 model 与 effort，不能从上一条后台 usage 推断偏好。否则真实聊天为 high，后台旧记录为 low，会在后续恢复中反复改变请求配置并影响缓存前缀。

生产原型保留了两个 stream control 请求：`set_model`、`apply_flag_settings`。这是版本相关接口；控制响应必须是 success，否则显式失败。不要悄悄换一个模型继续计费。

## 静默时间

默认北京时间 01:00–09:00。提示词要求不在这一段安排闹钟；后台监视器还会在 01:03 后、当前没有用户请求时停止空闲进程，以防模型忘记取消安排。用户在夜间主动发消息仍可以得到普通回复。

注意：停止检查与模型输出并非原子动作，已经进行中的轮次可能结束；不能把这称为“夜间绝不发生任何请求”。强硬隔离需求应在调度入口额外添加时区校验和取消策略。

## 可见自动冒泡

`auto_idle_message.py` 的 systemd timer 每分钟检查一次，本地检查本身不调用模型。

```text
有正在运行的聊天? → 跳过
01:00–09:00? → 夜间跳过，或在 01:00 起短窗口内发送一次停唤醒晚安
当天 09:00 后还没有真实用户消息? → 等用户先开始
最近一条入站消息不足 50 分钟? → 跳过
最近模型调用不足 50 分钟? → 跳过
最近模型调用已满 55 分钟? → 不冒险重建，等真实聊天
usage 的会话与当前会话不同? → 跳过
否则 → 通过 relay 发送一条自动消息，模型正常回复并记账
```

晚安窗口仅在 01:00–01:03 检查中有机会触发，还要求 usage 新鲜且会话一致。早安 MESSAGE 常量在兼容列表里，但当前 check 函数没有独立的定时早安分支。不要在文档或 UI 中把保留常量当作已启用功能。

## 开关有三种不同含义

| 操作 | 实际影响 |
| --- | --- |
| 自主唤醒开关 | 改 `auto-wakeup-preference.json`，运行时重新安排 / 停止原生调度 |
| 停用 idle timer | 停止可见冒泡检查，不会删除已有模型会话 |
| 停用 silent timer | 停止静默缓存探测，不会自动关闭原生唤醒 |

UI 应同时显示 desired_enabled、实际状态、定时器是否 active、最后一次检查及最后一次真正发送的消息时间，避免一个“运行中”把三个机制混为一谈。

## 失效与竞争保护

- pending 与 waiting_users 优先，防止一条自主消息抢在用户回复前插进来。
- native runtime 持有共享会话锁时，静默脚本跳过。
- 每次 wake 有 180 秒 watchdog；普通聊天有更长的请求超时。
- 无法恢复已验证会话时，不创建新会话假装接续。
- 对原生 `ScheduleWakeup` 不可用的环境应显示能力缺失；可用显式可见的外部调度替代，但必须另行命名与计费。
